# Image inventory: what krytis adds outside the junctions

Everything below is a krytis element (`elements/…`), not something consumed as-is from
the `freedesktop-sdk.bst` or `gnome-build-meta.bst` junctions. The tables are generated
from the element graph by `mise run image-inventory`, and `checks.yml` runs
`mise run image-inventory --check` on every PR, so the element lists cannot drift from
the stacks. Only the description column is hand-written.

## How the lists are built

`mise/tasks/image-inventory` walks the graph from `oci/krytis/image.bst`:

- **Containers.** Every element under `elements/oci/` or `elements/stacks/` only
  aggregates. The walk descends through all of a container's dependencies.
- **Top-level elements.** A krytis element that a container lists directly. It is filed
  under the first container that lists it (depth-first, in dependency-list order), so
  `core/mise.bst` shows up under `stacks/base-system.bst` even though
  `stacks/dev-tools.bst` lists it too.
- **Runtime dependencies.** krytis elements reached from a top-level element or a
  junction replacement through `depends:` and `runtime-depends:` edges only. These are
  in the image. *Pulled in by* names the elements in the image that depend on each one
  directly.
- **Build-only dependencies.** krytis elements reached only through some
  `build-depends:` edge. They are staged to build something else and never land in the
  image.
- **Junction replacements.** Entries in a junction element's `config: overrides:` map
  that point at a krytis element. Stacks keep naming the upstream element, but the krytis
  element is what gets built. A replacement is listed whether or not the upstream element
  reaches the image: `overrides/rust-bindgen.bst` is a build tool.

Junction elements (any dependency with a `:`) are never followed. A krytis element that
only a junction element depends on is therefore missed. That can only happen through an
`overrides:` entry, and those are listed as replacements.

## Updating the lists

When a PR adds, removes or moves an element, or changes a dependency between krytis
elements:

1. Run `mise run image-inventory --write`. It regenerates the Inventory section in
   place. Existing descriptions are kept by element path, so an element that moves
   between sections keeps its text. Rows for elements that are gone are dropped.
2. Fill in the last cell of every new row. `--check` fails on an empty one.
3. Run `mise run image-inventory --check`. CI runs the same command.

`mise run image-inventory` with no flag prints the regenerated section to stdout
without touching the file.

The check can't tell whether a description is still true. If a PR changes what an
element does, its row's text is a review question.

### Top-level elements
