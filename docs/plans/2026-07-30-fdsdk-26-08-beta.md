# Plan: Track freedesktop-sdk 26.08beta on a `beta` branch

> Investigation date: 2026-07-30. Source: [freedesktop-sdk-26.08beta.1 release](https://gitlab.com/freedesktop-sdk/freedesktop-sdk/-/releases/freedesktop-sdk-26.08beta.1) (tagged 2026-07-22), fetched via the GitLab releases API for the full changelog (the web page truncates it).
> **Decision, 2026-08-12** — resolves both Open Questions below: migration starts **now**, without waiting for a stable fdsdk 26.08 release, on the standard issue-numbered branch/worktree (not the literal `beta` name floated when this plan was drafted). This plan's investigation and Blocker/Phase content still apply verbatim — only the branch name and start-gate changed. Tracking continues under issue #305 ("Upgrade Freedesktop SDK to 26.08"), which already covers this exact bump; no separate tracking issue was filed.


## Why

`main` tracks `freedesktop-sdk-25.08*` (`elements/freedesktop-sdk.bst`, currently pinned to `freedesktop-sdk-25.08.15-0-gda39a00d43df80bcf17898c2ebf7035df59a6a39`). 26.08beta.1 is the first beta of the next epoch and already contains a repo-wide breaking change that will hit nearly every krytis element. Standing up a long-lived `beta` branch now — rather than waiting for the stable 26.08 release — buys time to fix the breakage incrementally instead of absorbing it all at once when `main` eventually has to move.

**This is explicitly not a "flip the pin and go" migration.** The investigation below found a hard external blocker (gnome-build-meta hasn't moved to 26.08 yet, not even its alpha branch) that means `beta` will run a mismatched fdsdk/gnome-build-meta pair for a while. Treat `beta` as an experimental branch that surfaces krytis-side breakage early, not as a near-term `main` candidate.

## What changed in 26.08beta.1

Full changelog fetched via `GET /api/v4/projects/freedesktop-sdk%2Ffreedesktop-sdk/releases/freedesktop-sdk-26.08beta.1` (the GitLab release page itself only renders a truncated description client-side — use the API for the complete list, this is not accessible via a plain page read).

### Breaking changes (upstream's own list)

1. **`runtime-minimal.bst` is now `runtime-gnu.bst`.** The path `public-stacks/runtime-minimal.bst` still exists but no longer includes `bash`/`coreutils` — it's now genuinely minimal. The old full-userland element (minimal + bash + coreutils) moved to the new path `public-stacks/runtime-gnu.bst`. Confirmed by reading both files at the tag:
   - `elements/public-stacks/runtime-gnu.bst` (26.08beta.1): `depends: [public-stacks/runtime-minimal.bst, bootstrap/bash.bst, bootstrap/coreutils.bst]` — i.e. this is exactly what `runtime-minimal.bst` used to be.
   - `elements/public-stacks/runtime-minimal.bst` (26.08beta.1): the stripped-down version, no shell.

   **This is the dominant breaking change for krytis.** `grep -rl "public-stacks/runtime-minimal.bst" elements/` → **73 files, 78 occurrences** (as of this investigation). Every one of them is a `kind: manual`/`kind: script`/`kind: make`-style element whose `build-commands`/`config:` block needs a real shell to run (`mkdir`, `cp`, `sed`, …) — this is completely ordinary BST practice, not a krytis-specific pattern, which is why the blast radius is so wide.

2. **Elements removed:** `glew`, `glog`, `pyelftool` (replaced by `python3-pyelftools`), `python3-pytz`, `python3-six`. Checked: **zero references** in `elements/` (`grep -rln "glew\.bst|glog\.bst|pyelftool\.bst|python3-pytz|python3-six" elements/` → no matches). No krytis-side action needed here.

3. **Elements made private** (moved under fdsdk's internal `_private/` tree, no longer addressable as `freedesktop-sdk.bst:components/<name>.bst`): `git-minimal`, `vala-bootstrap`, `avahi-base`, `systemd-hwdb`, `lvm2-base`, `efitools-bin`, `python3-minimal`, `python3-build-bootstrap`, `python3-installer-bootstrap`, `rr`, `sbsigntools`, `cryptsetup-base`, `fwupd-efi`, `libsmbios`, `freetype-stage1`, `lvm2-stage1`, `bpf`, `gnu-efi`, `cmake-stage1`, `dbus-base`, `systemd-stage1`, `u-boot-qemu`, `cups-base`, `geoclue-base`, `shim`, `flex-base`, `glib-stage1`, `gobject-introspection-base`, `bluez-base`, `valgrind`, `polkit-base`, `systemd-base`, `apparmor-base`, `gamemode-base`, `u-boot-unmatched`, `pipewire-base`, `xdg-desktop-portal-base`, `ovmf`, `gcc-base`, `flat-manager-client-base`.

   Checked every name against `elements/`. Only two hit, and both are **already redirected** via `elements/freedesktop-sdk.bst`'s junction `overrides:` table to a `gnome-build-meta.bst` equivalent instead of resolving into fdsdk directly:
   ```yaml
   components/systemd-base.bst: gnome-build-meta.bst:core-deps/systemd-base.bst
   components/geoclue-base.bst: gnome-build-meta.bst:gnomeos-deps/geoclue-base.bst
   ```
   So krytis itself doesn't reference the private paths directly — but this pushes the risk onto gnome-build-meta's own element graph (see Blocker below): if gnome-build-meta's `core-deps/systemd-base.bst`/`gnomeos-deps/geoclue-base.bst` themselves depend on other elements that just went private (very plausible for bootstrap-adjacent packages like `systemd-base`), that graph breaks independent of anything krytis controls directly.

   > **Rebase note, 2026-08-01** — `main` has moved since this was investigated
   > (#417/#425). `components/systemd-base.bst` no longer redirects into
   > gnome-build-meta; it now points at `overrides/systemd-base.bst`, a krytis-local
   > mirror of gnome-build-meta's element carrying a backported systemd patch. That
   > mirror lists ~40 `freedesktop-sdk.bst:components/*` build-deps *directly in this
   > repo*, so on 26.08 the private-element risk is no longer purely gnome-build-meta's
   > — re-check that list against the private set before flipping the pin (`bpf-maybe`,
   > `apparmor`, `libapparmor`, `cryptsetup-lvm2-stage1`, `pyelftools` are the
   > adjacent-looking ones; `pyelftool` is gone in 26.08 but the mirror already uses
   > `python3-pyelftools`). The mirror is temporary: it disappears when the junction
   > reaches systemd v261. The `runtime-minimal.bst` count above is also stale — 77
   > files today, not 73.

### Non-breaking but relevant

- `buildstream-plugins-community: update to 2.3.1` — krytis's `elements/plugins/buildstream-plugins-community.bst` is **already pinned to 2.3.1**. No action.
- `Update podman to v6.0.1-0` — worth a note in the eventual PR/skill doc; krytis's own `stacks/bootc.bst` podman version comes from fdsdk, so this changes transparently.
- Hundreds of routine component version bumps (see the full changelog fetched during investigation) — not enumerated here, they don't need per-element action, only "does the build still succeed."

## Blocker: gnome-build-meta has not moved to fdsdk 26.08 yet

`elements/gnome-build-meta.bst` tracks `gnome-50` (currently pinned to `50.3-6-g941b83247fec95877533afb3803f7bc15e755c2f`, confirmed to be the exact tip of `gnome-50` as of this investigation via the GNOME GitLab API). `gnome-build-meta.bst`'s own `overrides:` block redirects several fdsdk component paths (`glib`, `gtk3`, `vala`, `systemd-base`, `geoclue-base`, …) to gnome-build-meta equivalents, and reciprocally gnome-build-meta overrides *its* `freedesktop-sdk.bst` junction to point at krytis's own — so gnome-build-meta will build against whatever fdsdk ref krytis picks, for better or worse.

Checked gnome-build-meta's branches on `gitlab.gnome.org` (not `gitlab.com` — see `include/aliases.yml`'s `gnome:` alias) for anything newer than `gnome-50`:

- `alatiera/gnome-51-alpha` exists (an unofficial, unprotected personal branch by a GNOME dev) — but **it still pins `freedesktop-sdk-25.08.13`**, not anything in the 26.08 series. Confirmed by reading `elements/freedesktop-sdk.bst` on that branch directly.
- No protected/official gnome-51 (or any 26.08-compatible) branch exists yet.

**Conclusion (as investigated 2026-07-30):** there was then no gnome-build-meta ref anywhere, official or unofficial, known to work with fdsdk 26.08beta. `beta` would have had to run fdsdk 26.08beta.1 against gnome-build-meta's `gnome-50` tip — an untested, unsupported combination. This is *why* `beta` should stay a standalone experimental branch rather than a near-term merge target — re-evaluate once gnome-build-meta cuts a real 26.08-compatible branch.

> **Update, 2026-08-12** — gnome-build-meta's `master` (not a dedicated `gnome-5x` branch — checked `git ls-remote --heads`, the highest numbered release branch is still `gnome-50`; no `gnome-51`/`gnome-52` exists) now pins `elements/freedesktop-sdk.bst` to `track: freedesktop-sdk-26.08*`, `ref: freedesktop-sdk-26.08beta.3-0-g4c7a4177c501510d68ebcba31c5b65ea23bc1b4f` — confirmed by reading the file directly at `master`. This partially resolves the blocker (upstream is now moving in the 26.08 direction, not stuck on 25.08) but does **not** fully clear it yet: `master` is GNOME's unstable development trunk, not a release branch, and today it reflects a single beta tag (`beta.3`, 2026-08-11) — one data point, not a confirmed direction. Treat this as **not yet actionable** for issue #305 Task 1 Step 2 until fdsdk cuts *another* `26.08` alpha/beta/rc tag and `master`'s pin moves with it — that second data point is the signal that gnome-build-meta intends to track 26.08 going forward rather than a one-off sync. Once that happens, `GBM_TRACK` becomes `master` (provisional, pending an eventual dedicated `gnome-51` branch) rather than the currently-blocked "no branch exists" state.
>
> `master`'s `overrides:` table also changed materially since this plan's `gnome-50` snapshot: `components/systemd-base.bst` and `components/xdg-desktop-portal-base.bst` moved to `components/_private/systemd-base.bst` / `components/_private/xdg-desktop-portal-base.bst` (consistent with the private-element list in "What changed in 26.08beta.1" above), and new `glycin`/`libglycin` overrides were added. Re-diff `master`'s full overrides block against krytis's `elements/freedesktop-sdk.bst` overrides when Task 1 Step 2 actually unblocks — don't assume the `gnome-50`-era table above is still accurate.

> **Resolved, 2026-08-25** — GNOME has cut an official `gnome-51` branch (`git ls-remote --heads` now lists `refs/heads/gnome-51`, alongside the pre-existing unofficial `alatiera/gnome-51-alpha`), and it pins `freedesktop-sdk-26.08rc.1-0-ge076d4978ee6945763486f6ebd755d189460e4e7` — the identical ref `master` carries. That is the supersede condition named in Phase 5, so krytis now tracks `gnome-51`, not `master`. fdsdk tracks `26.08rc.1` to match. The pair is no longer skewed and no longer rides an unstable trunk, which is what this Blocker was about; the section above is kept for the investigation record, not as current state.
>
> What remains is not a *blocker* but ordinary release-candidate risk: rc.1 is not the final 26.08, and the rc → final step must be re-audited like any other (it was going from beta.3 to rc.1 that deleted `efitools` out from under the secure-boot seal stage — see Phase 2). Batch-checking every junction reference at each new tag is the cheap way to keep that honest.

## Other krytis-internal touch points found

- **`project.conf`'s `branch: 25.08` variable** (line 38) is *not* consumed by any BST element (`grep -rn "%{branch}" elements/ include/` → no hits) — it's purely read by `mise/tasks/generate-image-version` via a plain-text `grep '^\s*branch:\s' project.conf` to build the `image-version` label/OS release string. Low risk, cosmetic-only, but must be updated for the version stamp to make sense on `beta` (e.g. `26.08beta`).
- This is a **different variable** from fdsdk's own `include/repo_branches.yml`, which defines `freedesktop-sdk-flatpak-branch` (currently `'26.08beta'` at the 26.08beta.1 tag) — unrelated to krytis's `branch:`, comes along automatically once the junction ref bumps since it's pulled in via `(@): - freedesktop-sdk.bst:include/repo_branches.yml`. No separate action needed for this file.
- **`files/fakecap-manifest.tsv`** (34MB, committed) attributes every installed file to its source BST element (see `docs/skills/chunkah.md`). If the `runtime-gnu` rename or gnome-build-meta skew changes which elements exist or what they install, this manifest goes stale and needs regenerating via `mise generate-fakecap-manifest` **after** a successful `mise lint`.
- **`.github/workflows/track-bst-sources.yml`'s `track-core-junctions` job** co-tracks `gnome-build-meta.bst` + `freedesktop-sdk.bst` atomically and opens a PR against `main`. It runs unconditionally against whatever the workflow's checkout is — it is **not** scoped to `main` by branch name, just by which ref triggered it (see the `github.ref == 'refs/heads/main'` guard on the PR-creation step specifically, not the tracking step itself). Left alone, this job would try to re-track `beta`'s `freedesktop-sdk.bst` back toward whatever glob is checked in — since `beta` will change the `track:` glob to `freedesktop-sdk-26.08beta*`, this is *desired* behavior (keeps `beta` current within the beta series) as long as the job only ever runs against `main`'s schedule/dispatch trigger and never gets pointed at `beta` implicitly. Verify the workflow's trigger scope before relying on this — don't assume, the guard is on the PR step, not the checkout.

### Phase 3 — Attempt a real build

- [ ] `mise load-image --container --force` (full cold build — expect this to take significantly longer than a normal build the first time, since nothing in this ref is cached yet).
- [ ] Triage failures the same way as Phase 2. This is where gnome-build-meta/fdsdk version skew is most likely to surface as actual build errors rather than graph-resolution errors (e.g. a gnome-build-meta element's build-commands calling something that moved).
  - **First real failure, 2026-08-26: `freedesktop-sdk.bst:components/abseil-cpp.bst`.** Not version skew, and not something Phase 2 could ever have caught — a new failure shape, recorded as shape 6 in `docs/skills/bst.md` § Auditing a fdsdk major-version bump.
  - abseil `20260526.0` (fdsdk `26.08rc.1`'s pin) has `#ifdef __BMI2__` / `#include <bmi2intrin.h>` at the top of `absl/container/internal/raw_hash_set.h`. GCC rejects that header directly: `#error "Never use <bmi2intrin.h> directly; include <x86gprintrin.h> instead."`. The build dies at `[203/344]` compiling `reflection.cc`.
  - Why krytis and not fdsdk: `__BMI2__` is only defined when BMI2 is enabled, and krytis builds everything `-o x86_64_v3 true` (x86-64-v3 implies BMI2). fdsdk's CI builds baseline `x86_64`, never compiles the line, and is green. Their pin is not wrong from where they stand — krytis is simply the first to compile that branch.
  - Fixed by `elements/overrides/abseil-cpp.bst` + `patches/abseil-cpp/bmi2intrin-via-immintrin.patch`, a one-line swap to `<immintrin.h>` (same `_bzhi_u32`/`_bzhi_u64`, portable umbrella). Deleting the include does not work — the BMI2 branch is live code. Junction override entry added; drift-checked by the new `mise run abseil-cpp-check`.
  - Deliberately **not** fixed by bumping abseil. Upstream removed the whole `__BMI2__` block in commit `09a054bc6` (2026-06-08) and `20260817.0` ships without it, so this is a window (`20260526.*` only), not a permanent fork — but jumping three months of abseil to fix one include would drag unvalidated change into a graph where a great deal links it. Delete the override when the junction's abseil reaches `20260817.0`; the check task fails at that point to remind you.
  - Verified: `mise run bst -- build overrides/abseil-cpp.bst` succeeds in 44s, and the full image build proceeds past abseil into protobuf and its other consumers.

## Non-goals

- **Not** merging to `main` as part of this plan. `beta` stays experimental until fdsdk 26.08 is stable *and* gnome-build-meta has caught up (as of 2026-08-12: gnome-build-meta `master` tracks 26.08beta.3, but no dedicated release branch exists yet — see Blocker section).
